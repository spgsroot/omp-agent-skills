# Координация мультиагентной работы

## Когда применять

**Правило приоритета: действие важнее исследования.** Если пользователь просит
СОЗДАТЬ агентов/команду/терминалы («создай команду», «запусти агентов») —
создавай немедленно: `orca terminal split --command "omp --a2a-name <роль>"`
или task tool спавном. Разбираться в механике харнесса/репо ДО создания —
ошибка: это запрос на действие, а не на разработку. Исследование уместно
только если способ создания реально неизвестен (нет скилла/флага в хелпе).

- N терминалов на одной цели (`--a2a-name` роли: builder, reviewer, …);
- параллельные скауты одним task-вызовом (tasks[]);
- workflow-скрипт с parallel()/pipeline();
- любая раскладка работы на 3+ агентов.

## Разложение задач (главное правило)

**Параллелится только то, что не пишет в одно место.** Перед фан-аутом:

1. Выпиши юниты работы. Каждый юнит: своя область файлов/файловая граница
   (или read-only), свой критерий готовности, своя верификация.
2. Юниты с общей мутацией (один файл, один ветка) — либо последовательны,
   либо юнит получает свою изоляцию (`isolation: worktree` / разные ветки).
3. Зависимости → волновая структура: волна K начинается, когда закрыты
   Consumes-интерфейсы волны K-1. Явно перечисли, кто кого ждёт.

## Роли и адресация

- Роль терминала = его `--a2a-name`; задача адресуется по смыслу:
  `a2a:builder`, `a2a:reviewer`, `a2a:llmops`.
- Задача идёт **главному агенту** терминала — он сам решает, взять или
  делегировать своим сабагентам. Явный спавн на чужом терминале — только когда
  нужен изолированный контекст (`a2aSpawn: true`).
- Ответ чужого терминала — его ответственность: не дублировать чужую работу,
  не перезапускать чужие юниты без причины.

## Трекинг и слияние

- Статус сети: `read agent://` (все соседи + свои), GetTask для состояния
  чужой задачи. Ручной поллинг — не чаще 2-5 с, а не цикл.
- Слияние результатов: каждый юнит коммитит сам в свою область; интеграция —
  отдельный шаг координатора (после закрытия волны), не по ходу.
- Конфликт/застревание юнита > 2 ретраев → эскалация человеку, не молчаливый
  третий ретрай.

## Бюджеты

- Один фан-аут = один вызов task/workflow, не N сессий подряд;
- лимиты автоматически соблюдаются (concurrency policy, ingress-guard) — если
  получен отказ «limit reached», не ретраить сразу, а ждать/перепланировать;
- статус-таблица юнитов (| юнит | агент | статус |) — в каждом прогресс-отчёте.

## Анти-паттерны

- Фан-аут «на всякий случай»: агент без юнита = сожжённые токены;
- Координатор делает работу сам: если юнит одному мне дешевле, чем диспетч —
  делаю сам (правило из dispatching-parallel-agents);
- Параллельная запись в один файл без изоляции — источник конфликтов.
