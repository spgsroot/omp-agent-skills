# Координация мультиагентной работы

## Когда применять

Если пользователь явно поручил независимые задачи агентам, запускайте их
одним вызовом `task` с массивом `tasks[]`, без повторного согласования.
Иначе сначала определите независимые области: число агентов само по себе
не делает задачу параллельной.

В текущем omp нет CLI-флага `--a2a-name`, адресов `a2a:*` и инструмента
`GetTask`. Для отдельных терминалов используйте доступный в окружении
скилл управления терминалами, проверив его интерфейс; не подменяйте
обычный `task` запуском терминалов.

## Разложение задач (главное правило)

**Параллелится только то, что не пишет в одно место.** Перед фан-аутом:

1. Выпиши юниты работы. Каждый юнит: своя область файлов/файловая граница
   (или read-only), свой критерий готовности, своя верификация.
2. Юниты с общей записью в файлы выполняются последовательно либо в разных
   рабочих деревьях. Параметры изоляции берутся из текущей схемы `task`:
   не добавляйте отсутствующее в ней поле `isolation: worktree`.
3. Зависимости → волновая структура: волна K начинается, когда закрыты
   Consumes-интерфейсы волны K-1. Явно перечисли, кто кого ждёт.

## Роли и адресация

- `name` в элементе `tasks[]` задаёт имя задачи; `agent` выбирает тип
  исполнителя из доступного списка. Для исследования — `scout`,
  для SDD — соответствующий `sdd-*`, а не обычный `task`.
- Общие ограничения и выбранный уровень строгости передайте в `context`,
  область и критерий готовности — в `task` каждого элемента.
- После запуска используйте возвращённый ID: `write agent://<id>` —
  уточнение работающему агенту; `read agent://<id>` — сохранённый результат.
- Работа в чужом терминале не адресуется через `agent://`: этот URI
  обслуживает субагентов текущего процесса.

## Трекинг и слияние

- Результаты `task` приходят автоматически. Пока агенты работают, продолжайте
  собственную независимую часть. Если своей работы не осталось, используйте
  `wait`, без опроса статуса в цикле.
- `read proc://` показывает запущенные задачи; `read agent://<id>` читает
  результат. Просмотр статуса не заменяет получение автоматического ответа.
- Слияние результатов — после завершения нужной волны. В общей рабочей
  копии коммиты делает один ответственный; в разных рабочих деревьях
  исполнители могут коммитить отдельно.
- Конфликт/застревание юнита > 2 ретраев → эскалация человеку, не молчаливый
  третий ретрай.

## Бюджеты

- Один запуск независимых задач = один вызов `task` с `tasks[]`;
- лимиты автоматически соблюдаются (concurrency policy, ingress-guard) — если
  получен отказ «limit reached», не ретраить сразу, а ждать/перепланировать;
- статус-таблица юнитов (| юнит | агент | статус |) — в каждом прогресс-отчёте.

## Анти-паттерны

- Фан-аут «на всякий случай»: агент без юнита = сожжённые токены;
- Координатор делает работу сам: если юнит одному мне дешевле, чем диспетч —
  делаю сам (правило из dispatching-parallel-agents);
- Параллельная запись в один файл без изоляции — источник конфликтов.
